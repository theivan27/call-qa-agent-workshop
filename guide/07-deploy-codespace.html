Step 7

Deploy from your Codespace

Your Codespace already has the Static Web Apps CLI. Create the app with one command, publish with another, and watch your own machine upload the site — no portal wizard, no deployment pipeline to debug.

About 15 minutes · Two commands and a short wait

1. What actually gets deployed

A Static Web App is two halves that ship together, and it helps to know which is which before you watch them upload:

src/The front end. Plain HTML, CSS and JavaScript — plus src/audio/, the five call recordings.
api/The Python functions behind /api/*. Azure runs these for you; you don't manage a server.

The recordings are about 5 MB in total, so the first upload takes a few seconds longer than you might expect. That's normal.

You don't have to push first

This deploys what's in your Codespace right now, not what's on GitHub. That's handy while you're iterating, but it also means your fork and your live site can drift apart. Commit and push when you're happy — .env and api/local.settings.json are both in .gitignore, so git add . won't leak your endpoint.

2. Create the Static Web App

One command. It creates an empty app with nothing deployed to it yet, which is exactly what we want — we'll fill it in the next step.

In the Codespace terminal

az staticwebapp create \
  --name swa-call-qa-ab1234 \
  --resource-group rg-call-qa-workshop \
  --location eastasia \
  --sku Free

Use your own suffix in the name, the same way you did for the Foundry resource in Step 1. The name becomes part of your public URL, so it has to be unique.

The Free plan runs in only a few regions

eastasia, westus2, centralus, eastus2 and westeurope. Pick the nearest one. This is independent of where your Foundry resource lives — they don't have to match, and a few hundred milliseconds between them makes no difference to a workshop.

3. Get the deployment token

The token is what lets the CLI publish to your app. Read it into a shell variable rather than pasting it around — it's a credential, and anyone holding it can overwrite your site.

In the Codespace terminal

SWA_TOKEN=$(az staticwebapp secrets list \
  --name swa-call-qa-ab1234 \
  --resource-group rg-call-qa-workshop \
  --query "properties.apiKey" --output tsv)

echo "${#SWA_TOKEN} characters"   # a number means it worked; 0 means it didn't

Printing the length rather than the token keeps it off your screen, which matters if you're sharing it in a room or recording the session.

4. Deploy

In the Codespace terminal

swa deploy ./src \
  --api-location ./api \
  --deployment-token "$SWA_TOKEN" \
  --env production

The CLI zips both folders, uploads them, and prints the live URL when it finishes. The first run takes two or three minutes, because Azure installs your Python dependencies — including requests, which the transcription tool needs.

5. Open your site

Open the URL the CLI printed. You should see the call list, with a player under each call — those are the recordings, served from src/audio/.

The agent won't answer yet. Ask it to review a call and you'll get an error. That's expected: the deployed API has no identity and no settings, which is exactly what Step 8 fixes. Seeing it fail here is useful — it makes the point that running code and authorised running code are different things.

6. Deploying again after a change

Every later deployment is the same single command. The token is already in your shell variable, so as long as you haven't restarted the terminal:

In the Codespace terminal

swa deploy ./src --api-location ./api --deployment-token "$SWA_TOKEN" --env production

If you closed the terminal, re-run the command from Step 3 to put the token back.

Why not deploy from GitHub Actions?

You can, and in real projects you usually should — a push to main publishes itself, with no laptop in the loop. We're doing it by hand here for two reasons. It's one command instead of a portal wizard and a generated workflow file, and when something breaks you read the error in your own terminal rather than hunting through a build log.

The repository still ships .github/workflows/azure-static-web-apps.yml for when you want the automatic route. It's set to workflow_dispatch:, so it only runs when you ask it to. To make it automatic, add a push: trigger and put the deployment token in a repository secret called AZURE_STATIC_WEB_APPS_API_TOKEN.

  • The agent returning an error when asked to review — Step 8 fixes that.
az staticwebapp create says the name is taken

The name is part of a public hostname, so it's global. Change your suffix — swa-call-qa- plus something nobody else would pick — and run it again.

swa: command not found

The Codespace installs the CLI in .devcontainer/post-create.sh. If the Codespace was still building when you opened the terminal, that may not have finished. Wait for the build to complete, then open a new terminal. To install it yourself: npm install --global @azure/static-web-apps-cli.

The deployment token is empty

Usually the app name or resource group is misspelled, so the command found nothing and returned an empty string. Run az staticwebapp list --output table and copy the name exactly. If you're signed in to more than one subscription, check az account show --output table is the one you created the app in.

I get a 404 at the site URL

Check you deployed ./src and not the repository root. The folder you pass to swa deploy has to be the one containing index.html. Deploying the wrong folder publishes a site with nothing in it, which Azure serves as a 404.

The players don't appear on the deployed site

The recordings live in src/audio/. Confirm they're there with ls src/audio — you should see five .mp3 files. If the folder is empty, the deployment uploaded a site without them, and the app hides a player it can't find rather than showing a broken control.
