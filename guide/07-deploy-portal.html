Step 7

Deploy from the portal

Create a Static Web App in the portal, point it at your fork, and let Azure set up the deployment for you. From then on, every push to main publishes itself.

About 20 minutes · Mostly waiting for the first build

1. Push your work first

Azure deploys what's on GitHub, not what's in your Codespace. If you changed anything in Steps 3 to 5 — a new compliance rule, a sixth tool — commit it now.

In the Codespace terminal

git add .
git commit -m "My workshop changes"
git push

Nothing to commit? Fine, move on. And don't worry about leaking your endpoint: .env and api/local.settings.json are both in .gitignore, so git add . skips them.

2. Create the Static Web App

  1. Go to portal.azure.com.
  2. Search for Static Web Apps and select it.
  3. Select + Create.

On the Basics tab:

SubscriptionThe same one you've used throughout.
Resource grouprg-call-qa-workshop — the same group, so Step 10 catches this too.
Nameswa-call-qa-ab1234. Part of your public URL, so make it yours.
Plan typeFree.
RegionAny nearby region. This is where the API functions run.

3. Connect your GitHub repository

Still on the Basics tab, under Deployment details:

  1. Set Source to GitHub.
  2. Select Sign in with GitHub and authorise Azure. It asks for permission to write to your repositories — that's how it commits the deployment workflow in a moment.
  3. Choose your Organization (your own username), your Repository (call-qa-agent-workshop), and Branch main.
It must be your fork

If the repository list doesn't include your copy, you're signed in to GitHub as someone else, or you skipped the fork in Step 2. You cannot deploy from a repository you can't write to.

4. Tell Azure where the code lives

Under Build Details, set Build Presets to Custom, then fill in these three fields exactly:

FieldValueWhy
App location/srcThe front end.
Api location/apiThe Python Functions.
Output locationleave emptyNothing is built — the files ship as they are.
The field that breaks deployments

Output location must be empty. A preset may have filled in dist or build; clear it. If you leave it set, the build fails looking for a folder this project never creates — the most common failure on this step by a wide margin.

  1. Select Review + create, then Create.

5. Watch the first deployment

Azure just committed a workflow file to your fork and started it. Go and watch:

  1. Open your fork on GitHub and select the Actions tab.
  2. You'll see a run named after your commit, in progress.
  3. Give it three to five minutes. A green tick means deployed.

Look in .github/workflows/ on your fork and you'll find a new file, azure-static-web-apps-<something>.yml. Azure wrote it, along with a repository secret holding the deployment token. Pull it into your Codespace so your local copy matches:

In the Codespace terminal

git pull

6. Open your site

  1. In the portal, open your Static Web App resource.
  2. On Overview, find the URL — something like https://nice-field-0a1b2c3.azurestaticapps.net.
  3. Select it.

Your app is on the internet. That URL is public — you can send it to anyone, which is exactly why you'll lock it down in Step 8.

The calls list won't load yet. That's expected.

The front end deployed fine, but the API has no way to authenticate. In your Codespace it borrowed your az login session; in Azure there's no such session. Step 8 gives it an identity of its own. Don't debug this — just carry on.

Checkpoint
  • The Static Web App exists in rg-call-qa-workshop.
  • The Actions run on your fork finished green.
  • Your site's URL loads the app's layout.
  • A new azure-static-web-apps-*.yml is in your fork.

How deployment works from now on

Push to main and the workflow republishes the site. Open a pull request and Static Web Apps builds a temporary preview environment on its own URL, then tears it down when the PR closes. That's a genuinely useful way to review a change to the agent's instructions before it reaches anyone.

About the repository's own workflow file

This project ships with .github/workflows/azure-static-web-apps.yml, which deploys using a token you paste in yourself. It's set to run only when you trigger it manually, so it won't fight with the one Azure just created. It's there as a fallback for anyone who can't use the GitHub sign-in route — locked-down organizations, usually. Ignore it.

If something went wrong

The Actions run failed

Open the run and read the failing step. Nearly always one of:

  • Output location wasn't empty. Fix it in the portal under Settings → Configuration, or edit output_location: "" in the generated workflow file.
  • App location or Api location is wrong. They are /src and /api.
  • An API dependency failed to install. Check api/requirements.txt is unchanged.

After fixing the workflow file, commit and push to trigger a fresh run.

I can't see my repository in the dropdown

Select Change account under the GitHub sign-in and use the account that owns the fork. If your organization restricts third-party apps, an owner has to approve Azure's access — in that case use the token route in the fallback workflow instead.

A second, failing workflow run appeared

Your fork is from an older copy of this project where azure-static-web-apps.yml still ran on every push. It fails because it has no token. Open that file and change its triggers to workflow_dispatch: only, or delete it — Azure's generated workflow is the one doing the work.

I get a 404 at the site URL

Either the first deployment hasn't finished — check Actions — or App location isn't /src, so Azure published a folder with no index.html in it.
