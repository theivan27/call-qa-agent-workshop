Step 8

Make the live app work

Your site is deployed but its API can't reach Foundry, because in Azure there's no az login to borrow. Give it an identity of its own, then stop strangers using it.

About 20 minutes · The most instructive step for real projects

1. The problem, stated properly

Everything so far authenticated as you. DefaultAzureCredential found your Azure CLI session and used it. Your deployed API is a process in a datacentre with no user signed in, so that same code finds nothing and fails.

An application needs its own identity. Azure offers two kinds, and the difference is worth knowing:

Managed identity Azure holds the credential and rotates it. No secret ever exists for you to leak. Always preferred — but the built-in API of Static Web Apps doesn't support it.
Service principal An identity with a client secret you hold. Works everywhere, including here. The secret is a liability you now own.

You'll use a service principal because of that platform limitation, and you should know it's the compromise, not the ideal. Section 6 says what to do differently in production.

2. Create the service principal

In the Codespace terminal

az ad sp create-for-rbac --name call-qa-reviewer-web

You get JSON back:

{
  "appId": "11111111-2222-3333-4444-555555555555",
  "displayName": "call-qa-reviewer-web",
  "password": "a-long-secret-string",
  "tenant": "99999999-8888-7777-6666-555555555555"
}
Copy all three values now

password is shown exactly once and cannot be retrieved later. If you lose it you must generate a new one. Paste appId, password and tenant somewhere temporary — and not into a file in your repository.

3. Let it use your Foundry project

That identity exists but can do nothing. Grant it the same role you gave yourself in Step 1. First get your Foundry resource's ID — substitute your own resource name:

In the Codespace terminal

az cognitiveservices account show \
  --name fdy-callqa-ab1234 \
  --resource-group rg-call-qa-workshop \
  --query id --output tsv

Then grant the role, using that ID and your appId:

In the Codespace terminal

az role assignment create \
  --assignee 11111111-2222-3333-4444-555555555555 \
  --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" \
  --scope "/subscriptions/.../resourceGroups/rg-call-qa-workshop/providers/Microsoft.CognitiveServices/accounts/fdy-callqa-ab1234"

That GUID is the Foundry User role. Microsoft is partway through renaming these roles from Azure AI User, so the ID is the one thing guaranteed to resolve either way — prefer it over the display name in scripts.

It needs a second role as well. The agent transcribes recordings with Azure AI Speech, which is a different data plane on the same resource, so the Foundry role alone won't open it:

In the Codespace terminal

az role assignment create \
  --assignee 11111111-2222-3333-4444-555555555555 \
  --role "Cognitive Services Speech User" \
  --scope "/subscriptions/.../resourceGroups/rg-call-qa-workshop/providers/Microsoft.CognitiveServices/accounts/fdy-callqa-ab1234"

Skip it and the app still runs, but every review falls back to the stored transcript and says so in the report — a useful thing to see on purpose once, if you have a minute.

Scoping to the one resource rather than the whole subscription is deliberate. This identity can use your Foundry project and nothing else — least privilege, applied where it costs you nothing to apply it.

4. Add the settings to your web app

You deployed from the terminal in Step 7, so set the settings there too. Fill in your own values and run it as one command — appsettings set adds or updates the names you list and leaves everything else alone.

In the Codespace terminal

az staticwebapp appsettings set \
  --name swa-call-qa-ab1234 \
  --resource-group rg-call-qa-workshop \
  --setting-names \
    FOUNDRY_PROJECT_ENDPOINT="https://fdy-callqa-ab1234.services.ai.azure.com/api/projects/call-qa-project" \
    FOUNDRY_AGENT_NAME="call-qa-reviewer" \
    AZURE_CLIENT_ID="<the appId>" \
    AZURE_TENANT_ID="<the tenant>" \
    AZURE_CLIENT_SECRET="<the password>"

These are the five, and where each comes from:

NameValue
FOUNDRY_PROJECT_ENDPOINTYour project endpoint from Step 1
FOUNDRY_AGENT_NAMEcall-qa-reviewer
AZURE_CLIENT_IDThe appId
AZURE_TENANT_IDThe tenant
AZURE_CLIENT_SECRETThe password

The API restarts by itself a moment later. Check they landed with az staticwebapp appsettings list --name swa-call-qa-ab1234 --resource-group rg-call-qa-workshop --output table — it prints the names, not the secrets.

Prefer clicking?

The same five live in the portal under your Static Web App → Settings → Environment variables, on the Production environment. Add them with + Add and select Save. Use one route or the other, not both at once.

Those last three names aren't arbitrary — DefaultAzureCredential looks for exactly those variables. Same code, same client.py, different credential source depending on where it runs. That's the whole appeal of the pattern.

5. Try your live app

Open your site's URL again and review a call. The calls list should populate and the agent should answer.

It's on the public internet now, running on your subscription, scoring calls. Worth a pause.

One real limitation

The built-in API cuts requests off at about 45 seconds. One or two calls per request is comfortable; Review all collections calls may well time out in production even though it worked in your Codespace. That's not a bug you can configure away — the fix is a linked Functions app, or a queue and a background job for batch work.

6. Require sign-in

Right now anyone with the URL can spend your model budget and read your sample calls. Fix it with a configuration file — no code.

In your Codespace, replace the contents of src/staticwebapp.config.json with:

{
  "platform": { "apiRuntime": "python:3.10" },
  "routes": [
    { "route": "/*", "allowedRoles": ["authenticated"] }
  ],
  "responseOverrides": {
    "401": { "redirect": "/.auth/login/aad", "statusCode": 302 }
  },
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/api/*", "*.{css,js,svg,png,ico,mp3}"]
  }
}

Then push it:

In the Codespace terminal

git add src/staticwebapp.config.json
git commit -m "Require sign-in"
git push

Wait for Actions to go green, then open your site in a private browsing window. You're sent to Microsoft Entra ID to sign in before you see anything. This guide is a separate site, so it's unaffected — you can keep reading.

Authenticated is not the same as authorised

authenticated means anyone with a Microsoft account — that's a very large group. For anything real, invite specific users and require a custom role instead. Read it as "no longer wide open", not "secure".

Checkpoint
  • Your live site loads the calls list and reviews a call successfully.
  • Five environment variables are saved on the Production environment.
  • After the config push, a private window asks you to sign in.

If something went wrong

"Insufficient privileges" when creating the service principal

Your account can't register applications in Entra ID, which is common on work tenants. Either ask an administrator to create one and send you the three values, or do the rest of the workshop on a personal subscription. The app works fine in your Codespace regardless — this step only affects the deployed copy.

The live site still can't load calls

Work through these in order:

  • Check for typos in the five variable names. They're case-sensitive.
  • Confirm you saved on Production, not Preview.
  • Confirm the role assignment in section 3 succeeded — it's easy to paste the wrong scope.
  • Role changes take a minute or two. Wait, then reload.
  • Still stuck? Open Monitoring → Log stream on the Static Web App and read the actual error.
It worked, then stopped

Client secrets expire — the default is a year or two. In a real system you'd track that date and rotate ahead of it, which is precisely the chore managed identity removes. For today, generate a fresh secret and update AZURE_CLIENT_SECRET.

I'm locked out after requiring sign-in

Visit /.auth/login/aad on your site to sign in directly. To undo it, revert src/staticwebapp.config.json to the version on main and push.

Requests time out on longer reviews

The 45-second limit. Ask for one call at a time. For production, link a separate Azure Functions app — which also lets you use managed identity and drop the secret entirely.

What you'd change for production

This workshop is a teaching sample. Before anything like it touches real call data:

  • Link a separate Functions app so the API can use managed identity, and delete the service principal.
  • Keep any remaining secrets in Key Vault, not in app settings.
  • Replace authenticated with named users and custom roles.
  • Swap the mock tools for your real QA system, with a least-privilege account per tool.
  • Handle batch work with a queue, not a long web request.
  • Keep the human in the loop on anything that affects a person's employment. The agent drafts; a person decides.
