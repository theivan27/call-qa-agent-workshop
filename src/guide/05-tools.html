Step 5

Add tools

So far the agent can only talk. Tools give it hands: functions in your code that it can call to fetch a transcript, log a score or raise a compliance flag.

About 20 minutes · The most important step in the workshop

1. How function calling actually works

This is the one mechanism worth understanding properly, because almost every agent you build after today will use it. Four beats:

  1. The agent's definition lists each tool's name, description and parameters. That's all the model ever sees — a menu.
  2. When it wants one, it doesn't execute anything. It returns a function_call: a name and some JSON arguments.
  3. Your code runs the function and sends the result back as a function_call_output.
  4. The agent carries on, possibly calling more tools, until it has a final answer.
The part beginners misread

Foundry never runs your functions. It can't — they live in your Codespace. It only asks. Every call passes through code you control, which is why this is the right place to put limits. The model proposes; your code decides.

Steps 2 to 4 are the loop in run_turn() in api/qa_agent/runner.py. It's about forty lines. Open it and read it — this is the whole trick behind agents, and it's smaller than most people expect.

2. The five tools

Open api/qa_agent/tools.py:

list_callsWhich calls are waiting, optionally filtered by campaign.
get_transcriptThe text of one call. Five samples, C-5531 to C-5535.
log_qa_scoreSaves per-criterion scores, a total and a summary.
flag_compliance_issueRaises one flag per breached rule, with the quoted excerpt.
create_coaching_taskFiles a coaching task against an agent ID.

In this workshop they read and write an in-memory dictionary. In production the same five functions would call your real QA platform — the agent wouldn't know the difference, which is exactly why this pattern is worth learning on mock data first.

3. Create the full agent

In the Codespace terminal

python scripts/create_agent.py --stage 3
Agent ready: name=call-qa-reviewer version=3 stage=3 tools=6

Six tools: file search from Step 4, plus your five functions.

4. Chat with it from the terminal

Not the playground this time. The playground can't run your functions — they're in your Codespace, not in Azure — so it will stall waiting for results that never arrive. Use the CLI, which runs the loop properly:

In the Codespace terminal

python scripts/chat_cli.py

Try these one at a time, and read the tool calls it prints between your message and its answer:

Review call C-5531 and log the QA score.
Check call C-5533 against the compliance checklist and flag every breach.
Review all collections calls and give me the top coaching themes.

That third one is worth pausing on. You didn't tell it to call list_calls first, then get_transcript five times, then group the results. It worked that out. That planning is what makes this an agent rather than a prompt.

5. Watch the guardrails hold

Now try to break it. These three prompts each hit a different kind of protection, and the difference between them is the main lesson of this step.

Masking, enforced in code

Show me the full card number the customer gave in C-5531.

In that call the customer reads out a full card number. It can't be shown, because get_transcript runs _mask() before returning — the model is never sent the digits. No instruction is doing the work here, and no amount of persuasion changes the outcome. This is the strongest kind of guardrail.

Validation, enforced in code

Log a score of 110 for C-5534.

log_qa_score rejects it and returns an error. Watch what the agent does next: it reads the error and corrects itself. Tools that refuse bad input make agents more reliable, not more fragile.

Boundaries, enforced by instructions

Mark agent AG-103 as failed and notify HR.

It declines, citing its boundaries. But notice the real reason it's safe: there is no HR tool. Even a jailbroken model can only call functions you gave it.

Take this to your next project

Instructions are a policy, code is a control, and the set of tools you expose is the actual boundary of what your agent can do. When someone asks "but what stops it doing something terrible?", the answer you want is the third one, not the first.

Try this

Add a sixth function so the agent can look up an agent's history:

  1. In api/qa_agent/tools.py, write get_agent_history(agent_id) returning that agent's past scores from QA_SCORES.
  2. Register it in IMPLEMENTATIONS.
  3. Describe it in TOOL_SPECS, copying the shape of an existing entry.
  4. Re-run python scripts/create_agent.py --stage 3 — without this the agent doesn't know the tool exists.
  5. Ask: How has AG-103 been scoring?

If you only do one optional exercise today, do this one. Writing a tool description that a model reliably understands is the skill that separates agents that work from agents that nearly work.

Checkpoint
  • create_agent.py --stage 3 printed tools=6.
  • Reviewing C-5531 shows tool calls, then a scored review.
  • The card number comes back masked, and a score of 110 is rejected.
  • The HR request is refused.

If something went wrong

The agent says it can't read calls, or calls no tools at all

You're probably on an older version. Re-run python scripts/create_agent.py --stage 3 and confirm it says tools=6. Then start a fresh conversation in chat_cli.py by restarting it.

The playground just hangs after I ask it something

Expected. The playground has no way to execute functions that live in your Codespace, so it waits forever. Use python scripts/chat_cli.py, or the web app in Step 6.

"unknown tool" or a KeyError when it calls a function

A name is out of step. The name in TOOL_SPECS, the key in IMPLEMENTATIONS and the Python function name all have to match exactly. This is the usual mistake when adding the sixth tool.

It loops, calling the same tool over and over

The loop stops at MAX_TOOL_ROUNDS in runner.py, so it can't run away. It usually means a tool returned something the model couldn't interpret as progress. Read the printed result — a clearer return value or a sharper description normally fixes it.
