Step 9

Evaluate

A demo that worked once isn't a product. The difference between the two is that you can prove the second one still works after you change something.

About 15 minutes · The step people skip and later regret

1. Why this isn't optional

You've changed the instructions, the knowledge and the tools today. Each change could have quietly broken something that worked an hour ago, and you'd have no way of knowing — agents fail softly. They don't crash, they just get a bit worse. Instead of re-reading output and hoping, run the same checks every time.

2. Run the test cases

In the Codespace terminal

python scripts/evaluate.py

Each case in evals/test_cases.json starts a fresh conversation, sends a prompt, and checks two things: which tools were called and what the reply contains. The cases assert that the agent:

  • Catches the missing disclosure and late verification in C-5532
  • Catches the threats and the personal e-wallet in C-5533
  • Suggests empathy coaching for C-5535
  • Refuses to make HR decisions
  • Never shows a full card number

Open the file. The cases are readable, and a QA manager could write new ones without help.

3. Run it again

Seriously — run it two or three times. Model output varies between runs, so you may see a case pass, then fail, then pass.

A flaky case is information

The instinct is to treat it as noise. Don't. A case that passes four times in five is telling you the instructions are ambiguous at that point, and that one in five of your real reviews will be wrong in the same way. Tighten the wording in instructions.md, recreate the agent, and run again. That loop — change, measure, repeat — is the actual craft of building agents.

4. Break a guardrail on purpose

This is the exercise that makes the point stick.

  1. Open api/qa_agent/instructions.md and delete the whole Boundaries section.
  2. Recreate the agent:

In the Codespace terminal

python scripts/create_agent.py --stage 3
  1. Run python scripts/evaluate.py again.

The HR refusal case should now fail. The card-masking case should still pass — because that one is enforced in Python by _mask(), not by instructions. One guardrail evaporated when you edited a markdown file; the other didn't notice.

Put the section back, recreate the agent, and confirm the suite goes green again.

In the Codespace terminal

git checkout api/qa_agent/instructions.md
python scripts/create_agent.py --stage 3
python scripts/evaluate.py
Careful with that command

git checkout on a file throws away all your uncommitted changes to it, not just the deletion. If you've been editing the instructions and want to keep that work, undo the deletion by hand instead.

5. Look at the traces

Tests tell you whether it worked. Traces tell you what it did.

  1. In ai.azure.com, open your project and find your agent.
  2. Open its traces or monitoring view.
  3. Open a single run and expand it.

You get each step in order, with the tool calls, how long each took, and the tokens used. Tokens are your bill, so this view is also your cost model — it's where you discover that one review of one call costs a fraction of a cent, and that reviewing fifty calls in one request is where your latency goes.

Full tracing needs an Application Insights resource connected to your project. If the view is empty, that's why. Skip it today rather than creating another billable resource you'll need to delete.

Checkpoint
  • evaluate.py runs and reports pass/fail per case.
  • You've seen the suite go red when you removed the boundaries, and green when you restored them.
  • You understand which guardrails live in instructions and which live in code.

Worth discussing

If you're here with colleagues, these are the questions that matter back at the office:

  • What would you measure in production? Agreement with human QA scores on a sampled set; compliance breaches caught versus missed; time from call to feedback; cost per review. Agreement with humans is the one that earns trust.
  • Which actions should always need a person? You have a defensible answer from today: anything affecting someone's employment. Where exactly is your line?
  • What happens when the agent is wrong? Who notices, how do they appeal, and what gets fixed? An agent with no correction path will be distrusted into disuse, regardless of accuracy.
  • Who owns the knowledge files? The most valuable thing you built today is the separation between policy and code. It only holds if a person is responsible for keeping those documents current.

If something went wrong

Every case fails

Something environmental, not behavioural. Run python scripts/check_setup.py, then confirm the agent is at stage 3 with python scripts/create_agent.py --stage 3.

It's slow, or I hit rate limits

Each case is a full conversation with several model calls, so the suite takes a few minutes. If you see 429 errors you're hitting your deployment's tokens-per-minute quota — wait a moment and re-run. You can raise the quota under Models + endpoints if your subscription allows it.

A case fails and I think the agent is actually right

Then the test is wrong, and that's a legitimate finding. These cases check for specific words, which is crude — a correct answer phrased differently will fail. Fix the expectation in evals/test_cases.json. Knowing whether to fix the agent or the test is a judgement call you'll make constantly.
